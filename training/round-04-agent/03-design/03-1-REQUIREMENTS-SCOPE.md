# B2-1 03-1 — 요구·범위·수용 조건 설계 V1.0

> 기획/교육용 문서. 실제 코드·실행·학습자 숙달은 미착수. 공식 PDF와 평가표가 우선.

## 10초 기대 결과
가계부 프로그램으로 수입·지출을 기록하고 찾아보며, 월 예산을 넘으면 경고한다. 터미널을 닫았다 열어도 세 종류의 데이터가 유지된다.

## 범위·공식 근거
- 필수 CORE: [REQ-01~23](../01-requirements/REQUIREMENT-TRACEABILITY.md), 공식 PDF 1~8쪽. 공식 PDF 9~10쪽은 참고 출력 예시.
- 기존 평가 E1 기능·오류, E2 구조·클래스, E3 generator/decorator/type hints, E4 저장·확장성.
- 선택 BONUS: BON-01~04(백업/반복내역/정렬/원자성 강화)는 필수 완료 이후.
- 제약: Python 3.10+, 표준 라이브러리만, JSONL 또는 CSV, CLI 기반. 웹 서버·DB·클라우드·외부 AI API는 공식 필수 아님.
- 예외: 원자적 교체는 권장 안전성 결정이므로 설계에 포함할 수 있으나 보너스 자체를 필수로 잘못 승격하지 않는다.

## 내부 수용 흐름
요구 ID → 코드 위치(향후) → 시험 ID → 실제 증빙 파일/SHA → 평가항목. 누락 없이 연결해야 문서 설계 PASS, 실제 실행 없이는 RUNTIME NOT_VERIFIED.

## 요구사항 분석 위험·V0.1→V1.0
- V0.1: 단순 가계부 CRUD 중심으로 범위 제안.
- P01: budget/category/CSV 누락 위험 → V1.0에 REQ-15~18 추가 확인.
- P02: generator/decorator/type hints를 단순 선택 기능으로 오인 → REQ-09/13/19/21 필수 연결.
- P03: PDF 이중/단일 하이픈 상충 → [해석 경계](../01-requirements/REQUIREMENT-TRACEABILITY.md) 명시.
- V1.0: REQ-01~23 + BON-01~04 + 평가 E1~E4 분리, 수용 조건과 증빙 매핑 확정(문서안).

## 5분 입문자 확인
용어: 요구사항(Requirement)은 반드시 작동해야 하는 약속; 수용 기준(Acceptance Criteria)은 이 약속이 충족됐음을 시험하는 조건.
비유: 장보기 목록이 요구사항, 계산대에서 누락 여부를 확인하는 것이 검증. 단, 실제 시험 전에 체크했다고 완료는 아니다.
질문: 문서에 기능 10개가 적혀 있으면 프로그램도 실제 동작한다고 말할 수 있을까? **아니요**. 실행 증빙이 필요하다.

## 인계/문서 검증
공식 PDF 번호·제목·필수 항목, 링크, 내부 ID 표시, BONUS 분리를 재검토한다. 다음 [03-2](03-2-CLI-FLOW.md). DOC 통과 여부와 실제 기능 상태 분리.

## 설계 선택과 공식 요구의 경계(보완)
- **공식:** 최신순 list/search, yield 스트리밍, 영구 저장 3파일, 오류+힌트, 정상 0/오류 비0, CSV 지정 스키마.
- **내부 설계:** 날짜 내림차순 최신순, UUID 기반 ID, 정렬된 JSONL, 불량 CSV 일부 건너뛰기·exit=2, export 기본 덮어쓰기 거부.
- 내부 정책은 공식 평가의 새로운 필수 요구가 아니다. 다만 선택한 규칙대로 실제 동작하는지는 05 시험에서 확인한다.
- 상세 재사용 프롬프트와 위험 검토: [03-1~03-8 프롬프트 V0.1/V1.1](DESIGN-PROMPTS-AND-REVIEWS.md).
