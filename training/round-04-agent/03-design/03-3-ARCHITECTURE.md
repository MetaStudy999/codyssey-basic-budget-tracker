## 저장 스키마(설계 선택: JSONL)
| 파일 | 최소 한 줄 예시 — 교육용이며 미실행 | 규칙 |
|---|---|---|
| transactions.jsonl | `{"id":"TX-abc123","date":"2026-10-30","type":"expense","category":"food","amount":5000,"memo":"예시","tags":["meal"]}` | id 유일; 거래 날짜 내림차순 정렬 |
| categories.jsonl | `{"name":"food"}` | 공백/중복 이름 처리, 사용 중 삭제 금지 |
| budgets.jsonl | `{"month":"2026-10","amount":20000}` | 월별 1개 활성 예산, 수정 시 대체 |

실제 ID 문자열 `TX-abc123`는 설명용이다. **ID 정책 제안:** `uuid.uuid4().hex` 기반 식별자를 생성하고 활성 거래와 충돌하면 재발급한다. 날짜 정렬이 ID의 숫자 증감을 요구하지 않도록 날짜와 ID를 분리한다. 동일 날짜 동률일 때는 **ID 오름차순**으로 일관되게 정렬한다(공식 문서의 추가 규정이 아닌 내부 선택).

## '최신순'과 스트리밍을 동시에 만족하는 계획
공식 PDF 4~5쪽은 `list/search`의 **최신순 + yield 기반 순차 읽기**를 함께 요구한다. 단순히 `append` 파일을 뒤에서 읽으면 입력 날짜가 뒤섞였을 때 날짜 최신순을 보장하지 않는다.

**설계 결정:** 거래 날짜 내림차순 + 같은 날짜 ID 오름차순을 내부 정렬 규칙으로 선언한다. add/import/update/delete 시 **임시 파일에 정렬된 결과를 스트리밍 병합하여 기록한 후 `os.replace`로 교체**한다. list/search는 이미 정렬된 파일을 처음부터 한 줄씩 읽고 `yield`한다. import 다건 자료는 필요시 표준 라이브러리만 이용한 청크 정렬 또는 한 건씩 병합하되 대용량 성능의 한계를 E4에 기록한다. 삭제도 정렬 질서를 유지한다.

- 예: 먼저 10월 30일, 나중에 10월 1일 거래를 입력해도 조회 순서는 **10월 30일 → 10월 1일**.
- 임시 파일은 **같은 파일시스템·디렉터리**에 작성하고 유효한 데이터를 기록한 후 flush/fsync와 os.replace를 적용하는 안을 선택한다. 실패 시 원본 보존·임시 파일 정리. 이 설계도 다중 파일의 원자적 트랜잭션을 제공하지 않는다.
- 메모리 제한: list/search 자체는 전체 적재 금지. 정렬된 원본 + 순차 generator로 소비량을 줄인다. add/update/import는 파일 재작성으로 느려질 수 있음(기존 평가 E4 질문 대응).

## 저장 경로와 파일 책임
- 기본 데이터 폴더: `./data`; 명시적 `--data-dir`로 지정 가능.
- 내부 데이터 3파일은 지정된 데이터 폴더 내에서만 생성·수정한다.
- CSV 가져오기 `--from`은 입력 파일을 읽고, CSV 내보내기 `--out`은 사용자가 지정한 출력 파일에 기록한다. `--out`을 데이터 폴더 내부로 강제하지 않는다. 단, 덮어쓰기 정책과 위험 경로 점검은 03-5에서 지정한다.
- 프로그램 종료→재실행 후 3종 파일 동일 상태를 실제 검증해야 함.

## 저장 형식 비교와 선택 이유
JSONL(JSON Lines)은 한 줄씩 읽는 객체 기록에 적합하지만 임의 수정과 날짜 정렬 유지를 위해 재작성 비용이 있다. CSV(Comma-Separated Values)는 표 호환성이 좋지만 태그/따옴표 이스케이프 주의가 필요하다. 공식 교환은 CSV 스키마로 고정한다. 표준 라이브러리만 사용한다.

## 역할 예측 연습(교육용)
